A

采用机制，保持现有分层

ASPIRE 适合细化本机 Agent 的执行循环，以及系统的技能演化。 系统级 Agent 继续负责异构多机目标、分工和协作。 本机 Agent 负责当前任务的观测、动作编排、结果核验和有限修复。

本页是目标设计参考，新增机制标记为 D。 既有代码状态保持不变，未安装或运行 ASPIRE 实验。 交互内部留给外部实现；能力、AMO、HAL/SAL 仍按原职责工作。

核查日期：2026-10-18。 官方提交 fa00f0e · ASPIRE v1.0 release 于 10 月 16 日发布。 本次未发现独立版本 tag，因此引用固定提交。

独立复现与搜索 fix loop、候选程序搜索、留出测试、独立技能验证 候选先验证再入库，不能用同一成功案例证明泛化

核心循环与三项机制见官方方法。 接口、运行工件和实验流程分别见API、记录契约和迭代流程。

这里的持续学习主要改进程序与经验库；底层视觉和语言模型仍可使用网络权重。 本文不把官方 benchmark 指标作为本系统的性能或验收结论。

需要区分两种“多 Agent”：官方并行练习不同任务，属于技能发现流程。 它不等于 G1 与 M20 在同一世界分工、避让或交接物体。 本次所读会话面向一个配置工位；异构机器人协作仍由我们的系统层设计承担。

本机 Agent：从步骤执行细化为反馈驱动的技能编排

下图是目标循环；当前已有能力执行与声明恢复，通用推理/修订仍为 D。

内部环节 输入与输出 软件归属与设计要求
上下文组装 assignment、步骤结果、观测引用 → 当前事实 SW-05 的 local_context；只引用 perception/state/spatial 的结果
技能检索 当前目标、能力、本体与场景条件 → 经验和可用程序 SW-18 提供知识；SW-16 提供已发布工件描述；本机只读缓存
步骤提案 事实＋经验＋允许动作 → 类型化调用/修订 SW-05 local_planner；固定策略或模型 provider 均可
执行与监测 能力请求 → execution_id、反馈、终态 复用 capability_tasks/router；推理不阻塞动作执行或取消
效果核验 实测结果＋目标条件 → 满足、未满足或未知 本机消费能力后置条件；SW-04核验系统目标
有限修复 失败阶段＋剩余预算 → 重观测、替代候选或声明分支 SW-05；改变业务目标、跨机改派或生成新版本时升级

当前任务内的合法参数调整、候选选择和已有分支直接走本机循环。 新增可复用程序版本才进入系统演化，不要求每个下一步提案都重新发布。

程序的内容是“何时观察、调用什么、如何分支和恢复”。 IK、视觉、点云、轨迹和关节控制仍由专业模块实现。 若组合需要更细粒度动作，只暴露已有公共原语或先完善能力契约。 新任务程序不把 pick 的内部算法复制到 Agent，也不把整任务塞进 approach。

第一阶段沿用 PlanDraft、SkillInvocation 和 schema3 的声明分支。 当前编译器只支持受控模板，并不接受任意生成代码。 需要通用循环、在线图修订时，再扩展类型化任务契约和验证。 不先搭建第二套 Python 执行器或新的任务解释器。

观测按决策需要刷新：有效反馈已经回答下一步问题时直接复用。 旧观测保留真实时间；场景变化或证据矛盾时重新感知。 遮挡、抓空和跟踪丢失的具体处置仍由能力契约定义。 这一点参考官方工具使用规则。

D

系统 Agent：协作执行与技能演化分开推进

系统 planner 选择已验证技能并分配机器人。 只有可复用的失败模式才进入演化；每次失败不必都启动代码生成。

工作 原模块 参考 ASPIRE 后的细化
多机规划 SW-03 team_planner 检索技能，按本体能力筛选，再完成角色与依赖分配
执行协调 SW-02 team_runtime 管理跨机任务、责任与修订；不作为实验进程管理器
失败归因 SW-21 reflection_engine 对齐阶段与证据，区分 API错误、观测不足、规划失败、执行偏差和目标不满足
候选生成 SW-22 candidate_builder 生成结构或参数不同的候选，记录假设、父版本和差异
验证与发布 SW-23 evolution_manager 组织基线对照、留出测试、经验复现与发布决策
证据与记忆 SW-19 / SW-18 保存运行证据及验证后的经验；不将候选直接写入正式技能库
激活 SW-20 / config_client 发布版本和实际生效回执分开，后续任务固定其版本

程序验证与经验复现分别出结论。 经验表述尚未复现，不阻塞程序本身的独立测试。 已通过程序也不能让未经验证的经验自动入库。

官方 evosearch 使用多候选与固定开发场景比较，见搜索流程。 我们借鉴“不同失败假设＋相同评价条件”，不把 K=8 或其种子编号写成系统常量。 跨机调度和候选搜索的计算资源调度是两个不同职责。

研发平台提供仿真、记录、对比和构建工具。 运行系统的 EV 模块拥有经验、候选与版本生命周期，并调用这些工具。 因此，RSI 不被移交成仅由研发人员手动执行的工具链。

E

技能不是单一对象：知识、程序与能力分开

对象 保存内容 归属与生效条件
技能经验 适用条件、动作策略、失败线索、反例、证据引用 SW-18 knowledge_memory；检索出来不等于可执行
技能程序候选 参数化编排、所需能力、条件/效果、预算、版本差异 SW-22；验证前不进入活动目录
已发布技能 SkillManifest＋可信实现引用＋验证范围＋哈希 工件经SW-20分发，SW-16登记描述；编译器不按任意路径导入代码
原子能力 稳定请求/反馈/结果接口、算法与本体适配 navigation/manipulation等runtime；机器人实时准入

同一技能包的知识、程序与验证范围使用共同的 skill_id/version 关联。 验证范围至少区分机器人本体、设备配置、API版本、SIM/REAL及适用场景。 可以迁移“抓取前检查空间”这类经验，不能跨本体复制关节角、夹爪刻度或标定。

建议在既有结果上补充阶段证据引用和耗时归因。 关联关系为 mission → assignment → capability execution → primitive/provider span。 先记录阶段、输入摘要、返回值、首因和关键帧引用，不另建每帧全量日志系统。 是否保存完整视频继续按实验记录规范执行。

ASPIRE将程序返回、工具执行和任务成功分开记录。 其独立验证器只读技能说明重新解题，不读取原解法。 这检验知识是否表达充分；跨场景、跨本体泛化仍需要独立测试。 本系统将这种角色与现有 team_verifier 的在线目标核验区分开。

F

可以复用什么，不能直接搬什么

参考资源 采用方式 不直接照搬的部分
ToolRegistry 与 MCP schemas 从现有能力目录生成工具描述，必要时加薄 MCP 门面 不复制第二份能力注册表，不以 MCP 替代 ROS任务和SDK控制
LiveAgentSession 参考 job_id、非阻塞监测、观测年龄及执行后状态 不新建相机/设备所有者；不把单工位锁扩大成全队唯一动作锁
RunRecorder 与 CallTrace 借鉴父子调用、关键帧与耗时分解，扩展现有 evidence 不整块引入另一个记录系统或仿真步进主循环
iterative-debugging / evosearch 复用分区评价、失败归因和经验提炼方法，按需要移植工具 其提示文件是实验规程，不能当成已完成的机器人运行服务
真机工具与模型 参考契约表达及动作前后证据 YAM 六轴、夹爪、Mink/cuRobo配置不直接替换G1/REVO2/Pink/AMO

具体代码：MCP门面、实时会话、记录器。

真机 MCP 导出注册工具和固定程序，未暴露任意源码提交入口。 其固定程序目录只有 observe 和 go_home，见program_catalog.py。 SDK/关节控制并非必须作为我们正式 Agent 的工具。

README 对生成代码给出隔离要求；当前 ProgramExecutor 另有 AST/import 限制。 两者不应概括成已具备安全沙箱，见runtime.py。 我们的任务默认执行已批准版本，候选生成与验证不热改当前控制链。

NVIDIA项目代码采用Apache-2.0；第三方材料仍按各自条款，见LICENSE和NOTICE。

落地先后与真实状态

下表表示该机制的实现依赖，不替换全系统实施计划或物理验证顺序。

顺序 最小交付 当前基础与缺口
1 一次任务的阶段证据能解释失败 结果查询已有；可靠证据链与阶段引用待补
2 本机检索经验并提出类型化下一步 固定模板/声明恢复已有；模型、上下文组装与提案待接
3 一个失败模式产生候选并完成对照 reflection/candidate/evolution目前仍是M；需接真实工具
4 经验独立复现、候选发布及版本激活 Skill目录和知识检索已有；验证、发布链未接
5 同一技能在不同本体上条件化复用 多实例目录已有；多节点分配、协作与跨本体实验待做

这一设计补充两级 Agent 的工作机制，不改变现有物理能力验收结论。 ASPIRE自身的多任务成绩也不能代替本系统的G1、M20或warehouse验证。
