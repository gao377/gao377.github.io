B

知识、程序与原子能力分别管理

对象 内容 权威模块 版本与检索规则
SkillKnowledge 适用条件、动作意图、失败线索、恢复建议、反例和证据 SW-18 knowledge_memory 独立 knowledge_id/version；关联 skill_id 和兼容版本
SkillCandidate 基线、改进假设、程序/参数差异、所需能力 SW-22 candidate_builder 不可变 candidate_id、父版本与摘要；不能作为活动技能检索
SkillArtifact SkillManifest、可信实现引用、参数 schema、验证范围 SW-16 登记描述，SW-20 分发工件 skill_id/version/digest；以本机实际激活版本为准
AtomicCapability 请求、评估、反馈、结果、取消及具体算法 各能力 runtime 稳定接口版本与实时 readiness；不归知识库执行

以上三个 Skill 名称是目标数据对象，不是当前已存在的 Python 类。 现有 SkillManifest、MemoryRecord 和目录负责其最小实现起点。 经验与程序独立版本化，通过引用关联，不强制一对一发布。 改进经验表述不要求发布新程序；程序通过也不自动证明经验有效。

经验检索先按本体能力、接口、来源和场景条件筛选，再按任务相关性排序。 检索结果是有来源的建议，不是控制授权或当前测量。 模型可以读“上次在哪里找到物体”，不能据此直接生成本次抓取局部坐标。

证据如何变成可验证的假设

模块 内部职责 输入 → 输出 复用与拟设文件
SW-19 evidence_store 关联步骤、能力阶段与关键观测 EvidenceSpan/结果引用 → 可查询执行证据 runtime.py；repository.py 拟补可靠存储
SW-21 reflection_engine 归类首因、提出经验候选、区分事实与假设 同版本证据 → ReflectionReport runtime.py；failure_analysis.py 拟设
SW-22 candidate_builder 将不同假设转成有限候选 ReflectionReport＋基线 → SkillCandidate runtime.py；validation.py 拟设
SW-23 evolution_manager 组织对照、复现及发布决定 候选和验证范围 → 两类报告与决定 runtime.py；evaluation.py、release.py 拟设

EvidenceSpan 关联 mission → assignment → step → capability execution → phase/provider。 记录输入摘要、实际输出、错误首因、源时间和关键帧引用。 模型推理、规划计算、动作执行和记录开销分别计时。 墙钟耗时与仿真源时间分开，不跨时钟直接相减。 不新增每帧全量录制器，也不复制图像和地图算法。

归因至少区分：请求非法、观测不足、规划无解、执行偏差、目标未满足、基础设施异常。 因果尚未确定时保留 hypothesis，不把“发生在同一阶段”写成根因。 缺证据先提出补观测需求，不自动启动代码生成。

首版候选只改业务 Skill 编排和已声明可调参数。 新能力算法、VLA 训练和控制策略变化需独立研发与资格验证。 候选生成不能通过放宽成功标准、保护或标定来提升通过率。

程序验证与经验复现各自出结论

验证轨道 输入与执行 回答的问题 输出
程序对照 相同条件下执行基线及候选；先开发集再冻结留出集 候选是否更有效，是否损害原能力 ProgramValidation：目标结果、失败、耗时、适用范围
经验复现 新会话只读经验、任务和公共接口，独立形成解法 经验是否足够明确，能否指导另一 Agent KnowledgeValidation：复现结果、歧义和反例
在线目标核验 SW-04 查询实际能力结果并检查 GoalPredicate 本次业务任务是否满足目标 原 VerificationReport

独立经验复现由 SW-23 的验证 job 组织，不增加在线 team_verifier 服务。 验证器不能读取待验证经验对应的原始解法程序。 留出集不用于逐次修复；开发集效果与留出结果分别报告。 同工位复现不能证明跨场景或跨机器人泛化。

比较固定目标判据、场景/任务集、机器人与设备配置、软件版本和预算。 涉及随机性时记录种子；不同环境或来源的结果不能混成同一通过率。 硬条件通过后，再按声明的成功率、耗时、重试和资源代价比较。 权重和指标由评价配置声明，不把 ASPIRE 的候选数写为系统常量。

程序轨道不等待经验文稿通过；经验轨道也不会替程序补签通过。 二者可以独立发布各自已验证产物。 验证工具返回失败、未知或基础设施错误时，保留原结论。

E

发布与激活是两个步骤

程序状态：DRAFT → VALIDATING → ACCEPTED 或 REJECTED → RELEASED。 实例状态：RECEIVED → VALIDATED → ACTIVE 或 REJECTED。 这些是目标生命周期，不是现有 ROS 状态枚举。

责任 决定 约束
SW-23 接受或拒绝候选、记录发布决定 决策依据为独立验证及现有批准责任
SW-16 登记可用 Skill 描述 可信实现引用；不动态导入任意路径
SW-20 / config_client 分发、检查兼容性、报告实际激活 按 robot_id/instance_id/version/digest 对账
SW-02 / SW-05 固定任务所使用的版本 在途任务继续原快照，不热换程序或下肢策略

适用范围写明能力契约、本体设备、SIM/REAL 和场景条件。 已批准但未激活的版本不能出现在该机器人当前可执行目录中。 激活失败保留原版；回滚也要有实际生效回执。 持物与未结束动作先沿原责任链收尾，不因升级自动释放。

F

异构多机复用语义，分别验证执行

同一 Skill 可以声明探索者、导航者、操作者等角色。 SW-03 依据实际能力和空间关系选择实例，再由编译器绑定实现。 G1 与 M20 可以共享寻找目标、失败恢复等经验。 关节角、手指刻度、坐标标定和未经验证的动作参数不跨本体照搬。

迁移对象 可共享部分 接收方必须确认
导览/探索经验 观察顺序、语义目标、失败提示 地图关系、传感覆盖、导航与探索能力
操作技能 对象条件、步骤意图、结果要求 操作能力、手型、局部感知、已验证参数范围
程序工件 契约兼容的业务流程 版本、角色、设备与执行来源范围

并行候选试验只在独立仿真实例或明确资源分配后执行。 不能将 ASPIRE 多任务练习直接当作两台机器人同世界协同。 系统任务调度与实验资源调度各自负责自己的状态。

设计落地与验收范围

先补什么 复用现有实现 最小验收
阶段证据 evidence_buffer/store、能力结果 同一任务能追到失败阶段，重复上传不重复动作
本机反馈决策 SW-05 执行器、readiness、声明恢复 失败后选合法恢复；未知结果不当成功
候选对照 现有 Skill 编译器、固定任务入口、实验工具 相同条件比较基线/候选，保留失败与来源
经验复现 MemoryRecord、检索、独立模型会话 不读原解法仍可验证经验，失败不能进入已验证集合
版本激活 SW-16/20、config_client 新任务用新版，在途任务不被改变

不新增 AgentRuntime、第二套能力注册表或第二套 Python 机器人执行器。 图与文档描述目标职责；实施时逐项替换已有 mock，并更新状态标记。 本设计不改变探索、导航、操作及新版仿真的既定验收顺序。
